# JJ / 天天象棋多皮肤校准设计

## 问题定义

识别系统当前只持久化 `%APPDATA%/XiangqiAssistant/config.json` 和
`samples.npz` 一套模板。`source_id` 标识的是 ADB 设备或模拟器窗口，不标识
模拟器内正在运行的游戏。JJ 象棋和天天象棋在同一模拟器中切换时会得到相同
`source_id`，后一款皮肤的校准还会覆盖前一款。

天天截图中 `(2, 2)` 与 `(2, 6)` 两枚黑马使用当前特征的相似度为 0.9598，
而 `(2, 6)` 黑马与 `(2, 7)` 黑炮只有 0.4106。运行时却得到
`c=0.48 / n=0.34 / r=0.18`，证明输入像素足以区分棋子，错误来自跨皮肤模板
串用，而非图片不清或 Pikafish 棋力。

## 第一性原理约束

1. 截图层负责提供像素；皮肤会改变字体、底盘、颜色、缩放和棋盘几何。
2. 识别层必须把像素映射成唯一、合法、带置信度的 10x9 棋盘。
3. Pikafish 只接受合法 FEN 并在合法着法集合中搜索，不能修复错误棋子身份。
4. 不允许通过降低阈值把“不知道”伪装成“知道”；模糊时必须拒绝送入引擎。
5. JJ 的红、绿、白光圈是瞬态外观，不应成为新的棋子类别。

## 选定方案

保存多个完整 `Calibration` 档案，并在每次同步/首次启动分析时自动选择：

1. 先按执棋方向、采集源和截图尺寸过滤不可能的档案。
2. 对所有剩余档案运行现有完整识别流程。
3. 合法识别优先；多个合法结果中选择置信度最高者。
4. 所有结果都失败时保留最高置信度的原始错误，同时明确提示当前皮肤没有匹配
   档案，不能静默使用旧模板。
5. 校准成功后既写入内容寻址的档案目录，也保留顶层最新档案以兼容旧版本。
6. 启动时加载所有健康档案；损坏的单个档案不能拖垮其他档案。旧版只有顶层
   档案时自动作为一个候选加载。

## 光圈与 OCR 边界

JJ 光圈继续由现有三层防线处理：中心字形特征只取归一化 40x40 图中的半径
12 区域、棋子中心允许正负 3 像素搜索、多帧重试等待动画结束。红黑方判断只看
中央区域，避免外圈红光污染。

不引入通用 OCR。通用 OCR 对单个艺术汉字、描边、缩放和光圈没有确定性保证，
且不能解决棋盘几何和占位。每款皮肤在静止标准开局采一次监督模板，信息量更
完整、依赖更少，也能由合法性规则进行闭环验证。

## 数据布局与迁移

```text
XiangqiAssistant/
  config.json                 # 最新档案，兼容旧版
  samples.npz
  calibrations/
    <内容指纹>/
      config.json
      samples.npz
```

内容指纹由采集源、方向、截图尺寸、标签和模板字节共同计算。相同数据重复保存
不会新增目录，不同皮肤不会互相覆盖。

## 验收条件

- 两套相互不兼容的皮肤档案可以同时保存并重新加载。
- 同一采集源下，JJ 帧自动选择 JJ 档案，天天帧自动选择天天档案。
- 错误皮肤档案不再直接生成 FEN；无匹配档案时给出可执行的校准提示。
- 旧单档案配置仍可加载。
- 红、绿、白外圈不会改变中央棋子所属阵营或绕过身份置信度门槛。
- 现有象棋规则、FEN 预检、将军应对和 Pikafish 合法着法测试全部通过。
