# 高亮棋子漏识别安全修复设计

日期：2026-07-21  
分支：`dev-1.0`

## 目标

彻底阻止截图中真实存在的棋子被识别为空后，Pikafish 基于错误局面给出现场无法执行的建议。系统可以拒绝一次不可靠的分析，但不得显示可能错误的着法。

## 现场结论

现场 UI 显示原始 UCI 着法 `h7c7`，中文记谱 `炮二平七` 只是对该坐标着法的正确翻译，不是记谱层单独出错。

从 `analysis_snapshot.png` 重建真实盘面后：

- `h7c7` 的路径上有 `g7` 黑炮和 `e7` 黑象两个棋子，炮不能跨两个炮架吃 `c7` 黑马；项目的 `detect_move()` 也判定该着法非法。
- 真实盘面交给本地 Pikafish，推荐 `i0h0`。
- 只从盘面删除带白色高亮的 `e7` 黑象，Pikafish 在 5 秒搜索中返回 `h7c7 +3.85`，与现场 `h7c7 +3.88` 高度一致。
- 同一截图的 Hough 圆检测找到了全部 31 个棋子，包括 `e7`。问题不是“看不见棋子圆”，而是模板分类允许空标签覆盖了强占用证据。

Pikafish 不负责识别画面。官方实现用 `MoveList<LEGAL>` 构造搜索根着法，并用合法着法列表解析输入着法：

- `src/engine.cpp` 的 `Engine::set_position()` 校验局面后的历史着法。
- `src/thread.cpp` 的 `ThreadPool::start_thinking()` 从 `MoveList<LEGAL>` 创建根着法。
- `src/uci.cpp` 的 `UCIEngine::to_move()` 只返回当前局面的合法着法。

因此本次不修改 `/xiangqi/pikafish`。

## 根因

`Calibration.recognize()` 混合处理了两个不同问题：

1. 占用检测：该交叉点是否存在棋子圆。
2. 身份分类：该棋子是车、马、炮等哪一种。

当前流程先让包括空标签在内的模板竞争，再使用圆检测清除不可信的非空标签。即使圆检测明确确认某格有棋子，只要高亮导致空模板分数更高，该格仍会保留为空。

随后还有两处扩大影响：

- `occupancy_trusted` 为真时跳过总体模板置信度检查，仅执行棋盘结构检查。
- `validate_board()` 允许少子，因为吃子后的合法局面本来就会少子；它无法判断某个具体棋子是被吃掉还是漏识别。

最终，错误识别局面内部自洽，Pikafish 和 `best_advice()` 都只能在这个错误局面上判断合法性。

## 方案比较

### 方案 A：占用优先分类，并在无法确认身份时失败（采用）

圆检测可信时，已占用格只允许非空标签参与身份选择。若空标签原本胜出，则用最佳非空标签恢复；最佳非空分数仍低于校准阈值时，整次识别失败。库存与位置修正后，再检查所有圆占用格仍为非空。

优点：直接修复信息丢失点；高亮但字形仍可辨认时继续工作；无法可靠辨认时安全停止。改动集中在现有识别函数，无新依赖或新状态机。

### 方案 B：占用与空标签冲突时全部失败

不尝试恢复棋子身份，直接要求用户重试。

优点是最保守；缺点是轻微高亮或模板扰动也会中断，降低 Windows 10 实际可用性。

### 方案 C：连续多帧投票

采集多个稳定帧，对占用和身份做多数投票。

它会增加等待时间、线程状态和测试复杂度；对持续显示的落子高亮没有根本效果。因此不采用。

## 详细设计

### 1. 占用与身份分离

保留现有 Hough 圆检测、颜色约束、邻域偏移搜索和模板分数，不新增识别模型。

当 `occupancy_trusted` 为真：

- 对圆检测命中的格，选择分数最高的非空标签。
- 对未检测到圆的格，保持现有策略：只有模板分数显著高于阈值时才允许非空，以兼容选择圈遮挡导致的 Hough 漏检。
- 若某个圆命中格原本被判为空，且最佳非空标签分数低于 `self.threshold`，返回无效识别，错误信息指出无法确认的棋盘坐标。

这样，空模板只能回答“没有棋子”，不能在独立占用证据已经确认有棋子时覆盖棋子身份。

### 2. 库存与位置修正后的不变量

现有库存上限调整和仕/相合法位置修正可能再次把一个标签替换为空。完成这些步骤后检查：

```text
Hough 检测到的占用格 ⊆ 最终识别棋盘的非空格
```

若不成立，识别失败，不生成 FEN，不启动 Pikafish。允许右侧集合更大，是为了保留现有“模板很强但高亮导致 Hough 漏圆”的兼容路径。

### 3. 引擎前第二道防线

保留 `AssistantApp.best_advice()`：用识别棋盘模拟 Pikafish 返回着法，再交给 `detect_move()` 检查棋子走法、炮架、蹩马腿、塞象眼、己方被将等规则。

这层可以防止引擎协议或坐标异常，但不能代替识别层修复，因为它看不到截图中被漏掉的棋子。

### 4. 错误处理

识别身份不可靠时沿用现有失败链路：

```text
Calibration.recognize(valid=False)
→ sync_current_board() 不创建工作线程
→ UI 显示“检测到棋子但无法确认身份，请等待高亮消失后重试”
```

连续辅助模式同样不应用该盘面，继续走现有恢复/手动同步流程。不得用猜测局面调用引擎。

## 测试设计

1. **根因单元测试**：构造圆检测确认有黑象、但空模板分数高于黑象模板的场景；修复前黑象消失，修复后必须保留。
2. **安全失败测试**：圆确认有棋子，但所有可用非空身份分数低于阈值；结果必须 `valid=False`。
3. **现场着法回归**：使用现场重建盘面，验证 `h7c7` 因存在两个炮架而被 `best_advice()` 拒绝。
4. **现有兼容测试**：小光标圆不能凭空生成棋子；Hough 漏掉但模板很强的棋子仍可保留；红黑视角、库存和连续走子测试不得退化。
5. **完整验证**：运行全部 `unittest`、语法编译、`git diff --check`，并用本地真实 Pikafish 对真实盘面和漏象盘面做对照。

## 非目标

- 不修改 Pikafish 搜索算法或源码。
- 不增加神经网络识别、OCR、数据库或多帧投票框架。
- 不承诺从任意模糊截图强行猜出棋子；无法可靠确认时按已批准策略拒绝分析。

## 验收标准

- 本次截图中的 `e7` 高亮黑象不会再被静默识别为空。
- 如果无法可靠恢复该棋子身份，UI 不显示任何着法。
- 真实盘面上的 `h7c7 / 炮二平七` 不会通过应用合法性链路。
- 不修改嵌套 `pikafish` 仓库。
- 所有自动化测试通过，Windows 10 重新构建后完成一次现场手动回归。
