# 象棋任意局面、完整历史与失步恢复设计

## 目标

在同一棋盘皮肤已经完成过一次标准开局校准的前提下，允许辅助器：

- 从标准开局或可识别的任意中盘启动；
- 接受用户偏离推荐的任意合法走法；
- 保存完整实际走法历史；
- 正确处理重复局面和单步、多步悔棋；
- 正常恢复一次采样跨过 1～2 步的情况；
- 漏掉更多步时重新识别当前局面并建立新的历史基点；
- 自动识别失败时通过 FEN 和当前行棋方手工同步；
- 使用默认 5 秒、可配置的 Pikafish 搜索预算输出预算内最佳着法。

不承诺有限时间内数学意义上的绝对最优。丢失多个回合后若只有最终盘面，不伪造无法由信息唯一确定的旧历史。

## 第一性原理与不变量

系统可靠性的核心不是推荐算法，而是状态真实性。任何时刻都必须满足：

1. `GameState.board` 是引擎分析和 UI 回合判断的唯一逻辑棋盘。
2. `GameState.side_to_move` 表示该棋盘上的真实行棋方。
3. `base_fen + moves` 必须能够重放到 `GameState.board`。
4. 每次逻辑状态变化都令 `position_version` 严格递增，包括正常走法、悔棋和重新同步。
5. 同一个 `position_version` 最多分析一次；相同棋子摆法在不同版本中允许重新分析。
6. 视觉结果不确定时不猜测，不改变逻辑状态。

## 架构

### `game_state.py`

新增 `GameState`，成为唯一棋局语义状态源。它保存：

- `board: tuple`
- `side_to_move: str`
- `player: str`
- `base_fen: str`
- `moves: list[str]`
- `snapshots: list[Snapshot]`
- `position_version: int`
- `last_analyzed_version: int | None`

`Snapshot` 保存棋盘、行棋方和当时的走法历史长度。`GameState` 提供以下操作：

- `start(board, side_to_move, player)`：以当前局面建立基点。
- `apply_board(board)`：验证从当前棋盘到新棋盘是一手当前方合法走法，追加 UCI 历史、快照并递增版本。
- `restore_snapshot(board)`：当前棋盘匹配旧快照时截断历史、恢复行棋方并递增版本。
- `resync(board, side_to_move)`：以当前局面重建 `base_fen`，清空旧 moves，建立新快照并递增版本。
- `needs_analysis()` / `mark_analyzed()`：按版本控制引擎调用。
- `position_command()`：生成 `position fen <base_fen> moves <moves...>`。

不新增接口层、仓储层或事件总线。

### `board_recognition.py`

`MotionTracker` 只负责视觉观察，不再决定是否轮到用户分析。正常情况下继续输出 1～2 个候选棋盘。

连续 3 个采样周期都存在至少 2 个明显变化交点但无法还原合法走法时，执行一次现有 `Calibration.recognize(frame)` 全盘识别：

- 识别棋盘匹配 `GameState` 历史快照：交给 `restore_snapshot`，自动恢复悔棋。
- 识别出合法但未知的新棋盘：报告“需要重新同步”，不自行猜测行棋方。
- 识别失败：保持当前逻辑状态，提示手工 FEN 同步。

视觉跟踪器在正常走法、悔棋或手工同步成功后，都必须显式重置自己的棋盘和参考帧，使视觉参考与 `GameState.board` 一致。

### `pikafish_engine.py`

引擎入口接受完整的 UCI `position` 命令，不再只接受当前 FEN。搜索仍使用现有超时、重启、无控制台和进程回收机制。

默认 `movetime=5000`。UI 允许设置正整数秒，输入边界为 1～60 秒。超出边界或非数字时拒绝启动分析并显示中文错误。

### `app.py`

`AssistantApp.run_loop` 只编排以下流程：

1. 捕获画面并获取视觉候选棋盘。
2. 将候选依次提交给 `GameState.apply_board`。
3. 若候选匹配旧快照，调用 `restore_snapshot`。
4. 仅当 `GameState.needs_analysis()` 为真且轮到用户时调用 Pikafish。
5. 用户实际落子被接受后立刻清空旧推荐。

UI 增加：

- “当前行棋”下拉框：红方、黑方；标准开局自动使用红方。
- “搜索秒数”输入框：默认 5，范围 1～60。
- “同步 FEN”按钮：输入完整 FEN；FEN 中的 active color 决定当前行棋方。

从任意中盘启动时，程序先尝试使用已有校准识别完整棋盘。识别成功后使用用户选择的当前行棋方建立 `GameState`；识别失败时要求同步 FEN。

## 数据流

```text
截图
  -> MotionTracker 输出 0～2 个候选棋盘
  -> GameState 验证并记录实际 UCI 走法
  -> position_version 递增
  -> 若轮到用户且该版本未分析
  -> position fen <base> moves <history>
  -> Pikafish go movetime <1..60秒>
  -> 中文推荐与评分
```

失步恢复：

```text
连续无法解释
  -> 全盘识别
  -> 匹配快照：自动悔棋恢复
  -> 未知合法局面：要求确认行棋方后重建历史基点
  -> 识别失败：FEN 手工同步
```

## FEN 与合法性

新增 `fen_to_board(fen)`，只接受 6 个字段、10 行、每行 9 列、合法棋子字符和 active color `w`/`b`。同时复用现有棋子数量、双方将帅、将帅宫区和将帅不可直接照面的校验。FEN 的 6 个字段完整保留为基点；后续实际走法通过 moves 传给引擎。

任意摆子仍必须是 Pikafish 可接受的象棋局面。双方将帅缺失、棋子数量超限或无效 active color 会被拒绝，不把非法输入发送给引擎。

## 重复局面与悔棋

删除按棋盘数组永久去重的 `_prompted`。例如局面 A 在版本 3 和版本 11 出现时，两者是两个分析事件。

悔棋不减少 `position_version`，而是恢复历史内容后创建一个新版本。这样 UI 和引擎请求都不会把悔棋后的局面误认为已经处理过。

如果重新同步到未知局面，旧 `moves` 清空并以当前 FEN 作为新基点。旧快照不继续参与新基点后的自动悔棋匹配，避免把两段无法证明连续的历史拼接在一起。

## 错误处理

- 视觉变化不唯一：保持当前状态，显示“检测到棋盘变化，正在重新同步”。
- 自动全盘识别失败：显示“无法自动恢复，请同步 FEN”。
- FEN 无效：保持原状态并显示具体字段错误。
- 当前行棋方不匹配实际走法：不提交状态，等待恢复或 FEN 同步。
- Pikafish 拒绝局面：重启一次；仍失败则停止分析并保留棋局状态。
- 搜索秒数无效：不启动引擎请求。

## 测试

最小自动验证覆盖：

1. 偏离推荐的合法走法进入完整 UCI 历史。
2. 引擎收到基础 FEN、完整 moves 和配置后的 movetime。
3. 相同棋盘在不同版本重新触发分析。
4. 单步、多步悔棋恢复棋盘、行棋方和 moves 长度。
5. 悔棋后的版本号继续递增。
6. 未知局面 resync 清空旧历史并建立新基点。
7. 一次截图跨两步继续顺序提交。
8. 合法任意中盘 FEN 可启动，无效 FEN 被拒绝。
9. 搜索时间只接受 1～60 秒。
10. 用户走法接受后旧推荐被清空。
11. 现有捕获、旋转、高亮、引擎关闭和 Windows 无控制台测试继续通过。

Windows 人工验收使用重新构建的 EXE，覆盖标准开局、中盘 FEN、偏离推荐、悔棋、重复局面、模拟失步和搜索时间配置。

## 非目标

- 不训练或引入通用视觉模型。
- 不从一个最终盘面伪造已经丢失且不可唯一确定的走法历史。
- 不保证有限搜索时间内数学意义上的绝对最优。
- 不自动替用户点击或落子。
- 不支持从未校准过的新皮肤直接识别任意中盘。
