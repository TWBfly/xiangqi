# 自动回合与落子识别设计

## 目标

解决三个相互关联但本质不同的问题：

1. 对手完成合法落子后，程序自动接受走法、切换回合并给出推荐。
2. “当前行棋”显示真实内部状态，不再停留在启动时的人工输入值。
3. 标准开局校准时自动判断红黑视角，减少“我执”的人工配置。

同时增加可追溯诊断，使“没有识别到落子”能够区分为：没有发生棋子位移、画面变化不足、候选走法不唯一、走法不合法、全盘识别失败或截图条件变化。

## 截图事实与验收边界

用户提供的 `4.png` 中，红方一枚炮已经平移到中路；黑方棋子仍处于标准位置，黑方中卒仍在原交叉点，绿色圆环只构成选择/高亮信号。该帧不能作为“黑方已经完成棋子位移”的正样本。

系统必须遵守以下边界：

- 只出现选中光圈、棋子没有离开原交叉点时，不得伪造走法。
- 棋子从合法起点移动到合法终点并稳定两帧后，必须接受走法。
- GUI 信号与棋盘实际坐标冲突时，以棋盘合法走法为准并报告冲突。
- 只有最终静态棋盘且连续历史已丢失时，不能从信息中唯一恢复当前行棋方；此时才允许人工确认。

## 第一性原理

一个完整象棋走法必须产生至少两个语义变化：

```text
起点：原棋子 -> 空
终点：空/对方棋子 -> 原棋子
```

选中光圈、头像动画、倒计时或按钮变化不是走法，只能作为辅助信号。系统状态转换必须由“视觉证据 + 象棋合法性 + 时间稳定性”共同确认。

一旦 `GameState.apply_board()` 接受走法，它会翻转 `side_to_move`。因此“持续等待对手”严格表示视觉层没有提交一个被接受的对手走法，而不是 Pikafish 没有分析。

## 架构设计

### 1. 棋盘走法仍是主证据

保留现有主链路：

```text
截图
  -> 90个交叉点变化分数
  -> 当前方合法走法候选
  -> 两帧稳定确认
  -> GameState.apply_board
  -> 回合切换
  -> Pikafish
```

不改用纯 GUI 模板或通用目标检测模型。

### 2. 高亮干扰恢复

当前 `MotionTracker` 只覆盖“旧高亮先消失两帧，再发生对手走法”。新增测试与处理覆盖真实游戏中更常见的同一帧组合：

```text
上一手高亮消失 + 对手棋子移动 + 新落点高亮出现
```

实现原则：

- 继续从变化最大的交叉点枚举合法走法。
- 候选评分优先要求起点和终点都存在持续变化。
- 高亮附加变化只能增加噪声，不能单独构成走法。
- 连续两帧出现同一唯一合法候选才接受。
- 如果现有算法已经通过新增真实形态测试，不增加生产代码。

### 3. 实时回合状态

`GameState.side_to_move` 是唯一真实回合状态。工作线程在以下时机发送 `turn` 事件：

- 创建初始状态后；
- 每次走法成功接受后；
- 恢复历史快照后；
- 同步当前棋盘后。

主线程收到 `turn` 后更新界面。现有“当前行棋”控件改名为“局面轮到”，运行期间作为只读状态展示；只有停止状态下的任意中盘启动或 `needs_sync` 恢复场景允许用户选择。

这样界面不会再出现“下拉框显示红方、内部却等待黑方”的双重真相。

### 4. 自动判断“我执”

自动判断只在标准开局校准时执行。程序比较棋盘上、下两侧主要棋子字色的红色强度：

- 下侧明显为红色棋子：用户视角为红方，`rotated=False`。
- 上侧明显为红色棋子：用户视角为黑方，`rotated=True`。
- 差异不足：保留现有“我执”选择作为校准备用值，并明确提示“无法自动判断执棋方，已使用人工选择”。

自动判断成功后更新“我执”显示。运行期间该控件只读，避免用户修改显示但不修改既有校准坐标。

该算法依赖当前皮肤红黑字色明显这一已有事实，不新增模型或依赖。皮肤不使用红色区分双方时必须安全退回人工选择。

### 5. GUI 外围信号

JJ 象棋头像光圈、倒计时或其他回合动画只作为可选辅助证据，不直接驱动 `GameState`：

- 若能从棋盘外稳定区域得到回合信号且与历史一致，用于改善状态提示。
- 若没有已验证的红方/黑方成对样本，不启用猜测。
- 若 GUI 信号与合法棋盘走法冲突，报告冲突并保留棋盘状态。

本轮不实现绑定某个绝对像素坐标的模板识别。没有成对样本时写死 ROI 只会制造新的假自动化。后续若提供同一窗口尺寸下“红方行棋”和“黑方行棋”各一张完整截图，可增加一个隔离的辅助识别器，不改变棋盘主链路。

### 6. 可追溯诊断

`MotionTracker` 的识别结果增加简洁原因分类，不新增日志框架：

- `no_move`：不足两个有效变化点；
- `unstable`：已有候选但尚未稳定两帧；
- `ambiguous`：存在多个接近的合法候选；
- `illegal`：变化点无法组成当前方合法走法；
- `recovery_failed`：全盘识别失败，并保留具体错误。

UI 只显示对应中文信息。诊断数据至少包含变化位置和分数，供测试与问题复现使用；不默认持续写入大量截图。连续恢复失败时，仅保存最新一组参考帧和当前帧到配置目录，覆盖旧文件，避免无限增长。

## 数据流

```text
捕获当前帧
  -> MotionTracker 与最近已确认帧比较
  -> 没有棋子位移：继续等待，不切回合
  -> 唯一合法候选未稳定：显示等待稳定
  -> 唯一合法候选稳定两帧：提交 GameState
  -> GameState 翻转 side_to_move 和 position_version
  -> UI 收到 turn 事件并更新“局面轮到”
  -> 若轮到用户：Pikafish 搜索并显示推荐
```

恢复流程：

```text
连续三次无法解释
  -> 全盘识别
  -> 匹配历史：恢复快照并自动恢复回合
  -> 未知棋盘：缓存棋盘，只请求人工确认“局面轮到”
  -> 全盘识别失败：显示具体原因并保存最后一组诊断帧
```

## 错误处理

- 只有绿色选中光圈：保持当前回合，显示“检测到选中操作，等待棋子落点”。
- 棋子动画中间帧：等待第二个稳定帧，不提交状态。
- 当前方合法候选不唯一：继续采样，不猜测。
- 当前行棋方与检测到的棋子颜色冲突：进入恢复，不强行翻转回合。
- 自动执棋方判断不确定：使用人工选择并提示，不阻止校准。
- 截图尺寸或来源变化：停止识别并要求重新校准。
- 诊断帧保存失败：不影响棋局状态，只显示保存失败原因。

## 测试

最小自动验证覆盖：

1. 仅增加绿色选中光圈时不产生走法。
2. 黑卒完成前进一步并稳定两帧后被接受。
3. 旧高亮消失、对手走法和新高亮同帧发生时仍能识别唯一合法走法。
4. `GameState.apply_board()` 后 UI `turn` 事件从黑方更新到红方。
5. 初始、悔棋恢复和未知局面同步都会刷新实时回合显示。
6. 标准皮肤红方在下时自动判断执红。
7. 旋转视角红方在上时自动判断执黑。
8. 字色差异不足时安全回退人工选择。
9. 连续恢复失败保留具体原因和有限的最新诊断帧。
10. 现有完整历史、重复局面、悔棋、双步恢复、1秒搜索和无控制台测试继续通过。

Windows 人工验收必须使用重新构建的 EXE，分别验证：只选中不落子、红炮平移、黑卒前进、黑马跳步、吃子、旧高亮与新高亮同时切换、红黑两种视角，以及遮挡后的恢复。

## 非目标

- 不把选中光圈当作已完成走法。
- 不从单张静态棋盘伪造无法唯一确定的当前行棋方。
- 不为没有成对样本的 JJ GUI 区域写死像素坐标。
- 不引入深度学习模型、OCR 服务或联网依赖。
- 不改变 Pikafish 搜索和完整走法历史协议。
