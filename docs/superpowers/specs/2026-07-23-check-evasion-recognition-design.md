# 将军应对与高亮棋子识别修复设计

## 目标

彻底阻止两类错误进入用户界面：截图中的将军棋子因高亮或微小采样偏差被识别成其他棋子；任何走后仍使己方将帅被攻击的着法被当作合法建议。

## 现场证据

截图可重建为：

```text
1rb1k4/4a4/2Ra5/pNpC2p1p/4r4/8P/2P6/8B/9/2BAKA3 w - - 0 1
```

黑车位于 `(4, 4)`，与红帅 `(9, 4)` 之间没有棋子，红方正在被将军。真实 Pikafish 对该 FEN 返回 `f0e1`；当前应用的 `is_legal_xiangqi_move()` 却认为 `b6c4` 的马步合法，因为它只检查棋子几何走法和将帅照面，没有检查走后红帅仍受黑车攻击。

把 `(4, 4)` 从黑车 `r` 错写成黑卒 `p` 后，真实 Pikafish 返回 `b6c4`，分值与现场接近。这证明现场错误的首要来源是选中黑车被识别为黑卒，Pikafish只是正确分析了错误 FEN。

当前特征匹配只在中心分数低于 `0.70` 或第一、第二候选间隔小于 `0.08` 时搜索 ±3 像素邻域。高亮黑车在错误中心可能以高分、大间隔匹配黑卒，因此不会触发已有的邻域纠偏。现场截图的自模板实验表明：错误中心更像卒；在邻域 `(＋1,＋2)` 处，黑车相似度达到约 `0.95`，明显高于黑卒约 `0.43`。

## 官方 Pikafish 边界

官方提交 `97133eebb6ed55e0bfa13262555c77d683d6ac0f` 中：

- `generate<EVASIONS>` 在被将军时生成挡将、吃将军子和走将；
- `generate<LEGAL>` 根据 `pos.checkers()` 选择应将生成器，并用 `pos.legal()` 再过滤；
- 搜索根节点来自 `MoveList<LEGAL>`。

因此不修改 Pikafish。应用必须保证传入 FEN 与截图一致，并在输出边界独立验证完整象棋合法性。

## 方案比较

### 方案 A：复用现有邻域搜索并补全共享合法性检查（采用）

对 Hough 已确认存在棋子的格点始终执行现有 ±3 像素邻域搜索，不再让“高置信度错误类别”绕过纠偏。把 `is_legal_xiangqi_move()` 的最终判断改为复用已有 `_king_in_check()`，确保任何调用者都不能接受走后仍被将军的着法。

优点：最小改动、无新依赖、不改变校准格式，同时修复识别源头和规则边界。

### 方案 B：更换特征格式并强制重新校准

扩大或改造棋子特征向量。会使 Windows 上现有 `samples.npz` 失效，影响所有棋子，当前证据不足以承担该风险。

### 方案 C：新增 OCR 或第二套视觉模型

小尺寸艺术字体 OCR 仍可能误判，且会增加模型、打包和运行时依赖。它没有消除现有分类器的错误路径。

## 数据流与安全边界

```text
截图
  → Hough 占用检测
  → 所有已占用格执行 ±3 邻域模板匹配
  → 身份分数/间隔安全门
  → board_to_fen
  → Pikafish MoveList<LEGAL>
  → is_legal_xiangqi_move（几何规则 + 走后将军检查）
  → detect_move 二次校验
  → 中文记谱与箭头
```

任何一层失败都返回错误，不显示建议着法。

## 最小实现

1. 将识别邻域搜索条件扩展为：非空且该格被 Hough 标记为占用，或原有低分/低间隔条件成立。
2. 删除 `is_legal_xiangqi_move()` 中只处理将帅照面的专用扫描，改为构造走后棋盘并调用 `_king_in_check()`。
3. 不增加新类、新配置、新依赖，不修改 Pikafish。

## 验收标准

- 现场正确 FEN 中 `_king_in_check(board, "w")` 为真。
- `b6c4` 在正确局面中被 `is_legal_xiangqi_move()` 拒绝。
- 同一局面传给真实 Pikafish 不返回 `b6c4`。
- 高置信度错误中心、邻域存在正确黑车特征时，最终识别为 `r` 而不是 `p`。
- 普通未高亮棋子、马兵身份安全门、移动检测和真实引擎回归继续通过。
- `requirements.txt` 与嵌套 `pikafish` 仓库无变化。
