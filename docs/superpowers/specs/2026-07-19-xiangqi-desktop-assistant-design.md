# Windows 象棋桌面辅助器设计规格

**日期：** 2026-07-19  
**状态：** 已获用户设计批准  
**目标平台：** Windows 10、雷电模拟器、腾讯手游助手

## 目标

将现有 Flask 网页控制台改造成 Windows 置顶桌面辅助器。程序持续读取模拟器中的象棋局面，只在轮到用户时调用 Pikafish，并在置顶小窗口显示类似“炮二平五”的推荐着法。程序不打开网页、不播放语音、不自动操作棋子。

## 非目标

- 不训练或引入机器学习模型。
- 不自动点击、拖动或代替用户落子。
- 不提供网页、远程访问或局域网服务。
- 不同时维护网页界面和桌面界面。
- 不支持未经校准的任意棋盘皮肤和分辨率。

## 现有系统结论

现有 `build_exe.bat` 正确打包了 `app.py`，但 `app.py` 的产品形态是 Flask 服务。网页通过 `/api/scan` 手动触发全屏截图、模板匹配和 Pikafish 分析，因此打包成功后仍然需要浏览器。

在用户提供的 `image.png` 上，现有识别器检测到 0 枚棋子。固定模板最高匹配分数只有 0.289–0.474，低于 0.60 阈值。Pikafish 本身已独立验证可返回标准开局着法，因此改造重点是采集、校准、识别和连续回合控制。

## 总体架构

```text
模拟器
  -> ADB截图；失败时使用Windows窗口截图
  -> 已校准的9x10棋盘交点
  -> 逐格棋子识别和合法性校验
  -> 稳定局面及走子变化检测
  -> 判断当前行棋方
  -> Pikafish分析
  -> Tkinter置顶窗口显示中文着法
```

系统由四个运行组件组成：

1. `capture.py`：发现模拟器和获取截图。
2. `board_recognition.py`：校准、识别、局面校验、坐标规范化和走子变化检测。
3. `pikafish_engine.py`：可靠管理 Pikafish 子进程、获取最佳着法并生成中文记谱。
4. `app.py`：Tkinter 窗口、用户设置和连续辅助状态机。

## 模拟器采集

### ADB优先

程序按以下顺序寻找可用 ADB：

1. 已保存配置中的 `adb.exe` 和设备号。
2. 雷电模拟器常见安装目录中的 `adb.exe`。
3. 腾讯手游助手常见安装目录中的 `adb.exe`。
4. Windows `PATH` 中的 `adb.exe`。

发现 ADB 后运行 `adb devices`，只接受状态为 `device` 的设备。只有一个在线设备时自动选择；存在多个在线设备时在界面下拉框中要求用户选择。截图通过 `adb -s <serial> exec-out screencap -p` 直接读取 PNG 字节，不先写入模拟器存储。

### Windows窗口兜底

ADB 不可用时，程序使用 Python 标准库 `ctypes` 调用 Windows API 枚举顶层窗口，匹配雷电模拟器和腾讯手游助手标题，再用 Pillow 截取对应窗口矩形。存在多个候选窗口时由用户选择。

窗口截图依赖窗口可见且未最小化。程序检测到空白、全黑或尺寸变化时停止分析并提示重新显示或校准窗口。

## 校准流程

校准必须在标准初始局面进行。

1. 用户选择自己执红或执黑。
2. 用户点击“校准棋盘”。
3. 程序从当前采集源获取一帧截图并显示。
4. 用户拖动矩形，从屏幕上的左上棋盘交点框到右下棋盘交点。
5. 程序按 9 列、10 行等距生成 90 个交点。
6. 程序依据用户执棋颜色确定当前画面是红方在下还是黑方在下，并将内部棋盘统一规范为黑方在上、红方在下。
7. 程序按标准初始布局提取各棋种的多个圆形中心样本，以及初始空位样本。
8. 程序立即重新识别同一截图；只有识别结果严格等于标准开局 32 枚棋子时才保存校准。

校准配置写入 `%APPDATA%\XiangqiAssistant\config.json`，包含采集源、设备或窗口标识、棋盘矩形、方向、识别阈值和模板样本目录。更换皮肤、分辨率、Windows DPI、模拟器或棋盘方向后必须重新校准。

## 棋盘识别

识别器不再全屏寻找棋子，只处理校准后的 90 个交点。

每个交点截取固定比例的正方形区域，缩放为统一尺寸，并使用圆形遮罩忽略格线和方格背景。识别分为两步：

1. 根据校准得到的空位样本判断该交点是否为空。
2. 对非空交点，与当前皮肤的多个棋子样本计算 OpenCV 归一化相关性，选择最高分棋种。

程序保存每格置信度。以下任一条件成立时拒绝局面：

- 红帅或黑将不是各一个。
- 任一方棋子数量超过规则上限。
- 总棋子数大于 32 或小于 2。
- 任一非空格低于校准阈值。
- 两个连续采样帧的棋盘不同。
- Pikafish 拒绝生成的 FEN。

内部棋盘始终采用黑方在上、红方在下的 10×9 数组。画面为黑方在下时，识别结果先旋转 180 度再生成 FEN。

## 回合与局面状态机

校准后的标准开局从红方行棋开始。程序每 700 毫秒采集一次；仅当连续两帧识别结果相同，才认为局面稳定。

状态如下：

```text
STOPPED
  -> CALIBRATED
  -> WAITING_STABLE_BOARD
  -> USER_TURN
  -> WAITING_USER_MOVE
  -> OPPONENT_TURN
  -> WAITING_OPPONENT_MOVE
  -> USER_TURN
```

稳定局面发生变化时，程序比较前后两个棋盘：

- 一个己方棋子从起点消失，并在终点出现或替换对方棋子，视为一次己方走子。
- 一个对方棋子发生同样变化，视为一次对方走子。
- 不能还原为单次合法走子的变化视为动画、识别错误或悔棋，程序等待下一稳定局面，不切换回合。

轮到用户时只对该局面分析一次，并缓存局面 FEN，避免重复显示和重复调用引擎。用户未采用推荐着法仍然允许继续，只要实际局面变化可以识别为合法走子。

## Pikafish管理

保留现有 Pikafish 二进制和 NNUE 文件，并补充以下约束：

- 启动后必须在限定时间内收到 `uciok`。
- 设置 NNUE 后发送 `isready`，必须收到 `readyok`。
- 每次搜索设定明确的 `movetime`，不同时叠加固定深度。
- 读取输出设置超时，防止界面永久阻塞。
- 引擎崩溃时自动重启一次；再次失败则在界面显示错误。
- 关闭程序时发送 `quit` 并回收子进程。

引擎在后台线程运行，Tkinter 主线程只负责界面更新。

## 中文着法

引擎返回 UCI 坐标后，程序根据走子前棋盘生成中文记谱：

- 红方使用中文数字，黑方使用阿拉伯数字。
- 正确处理进、退、平和目标路数或步数。
- 同一路存在两个相同棋子时使用前、后区分。
- 内部坐标已经规范化，因此黑方在屏幕下方时仍输出棋手视角下的正确记谱。

## 桌面界面

Tkinter 窗口默认置顶，尺寸保持紧凑，只包含：

- 采集源或设备选择。
- 用户执红/执黑选择。
- “校准棋盘”按钮。
- “开始辅助/停止”按钮。
- 大字号推荐着法。
- 一行状态文字。

程序不绘制棋盘、不显示广告或远程控制、不启动浏览器、不播放语音。关闭窗口时停止采集线程并关闭 Pikafish。

## 错误处理

- 无在线设备或模拟器窗口：提示“未找到模拟器”。
- 多个候选设备：要求用户选择，不猜测。
- 截图失败：保留上次推荐，但状态标为“截图失败”，不重新分析。
- 校准验证失败：不保存半成品配置，提示回到标准开局后重试。
- 识别置信度不足：显示“等待稳定棋盘”，不调用引擎。
- 引擎超时或退出：自动重启一次，仍失败则停止辅助。
- 分辨率或截图尺寸改变：停止辅助并要求重新校准。

## 验证与验收

自动验证至少覆盖：

1. 使用 `image.png` 校准后识别出标准开局 32 枚棋子和标准开局 FEN。
2. 红方在下和黑方在下时规范化结果一致。
3. 标准开局判断红方先行。
4. 用户走子后进入等待对手状态，对手走子后重新进入用户回合。
5. 相同稳定局面不会重复调用引擎。
6. 非法或低置信度局面不会提交引擎。
7. Pikafish 标准开局能在超时内返回合法着法。
8. PyInstaller 成功生成不打开浏览器的 Windows GUI EXE。

最终人工验收流程：启动模拟器并进入标准开局，完成一次校准，开始辅助，按推荐或其他合法着法落子，等待对手落子，确认置顶窗口自动给出下一次推荐。

## 约束与取舍

使用一次性皮肤校准替代通用视觉模型。这能以现有 OpenCV、NumPy 和 Pillow 完成需求，代价是皮肤、分辨率或方向变化后需要重新校准。只有实际使用中出现大量不同皮肤且人工校准不可接受时，才考虑训练视觉模型。
