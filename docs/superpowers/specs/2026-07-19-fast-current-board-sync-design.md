# 快速响应与当前棋盘同步设计

## 目标

解决两个直接影响可用性的问题：

1. 将一次正常落子后的默认提示时间从约 6～7 秒降到约 1.4～1.8 秒。
2. 普通用户不再接触 FEN；程序负责识别棋盘，用户只选择“当前轮到红方或黑方”。

本次只改现有采样、搜索预算和恢复入口，不引入新模型、新依赖或 JJ 象棋专用界面识别。

## 第一性原理

响应时间由三段相加：

```text
发现落子时间 + 稳定确认时间 + 引擎搜索时间
```

当前实现每 0.7 秒采样、连续两帧确认，再默认搜索 5 秒，因此正常总延迟约为 6～7 秒。方案 A 将采样周期改为 0.2 秒，保留两帧确认，并把默认搜索改为 1 秒，所以目标延迟约为：

```text
0～0.2 秒发现 + 约 0.4 秒确认 + 1 秒搜索 = 约 1.4～1.6 秒
```

操作系统调度、截图和 UI 刷新会带来少量波动，人工验收上限定为正常环境下 2 秒左右。

静态棋盘包含棋子位置，但不包含“当前行棋方”这一时序信息。同一张棋盘图既可能轮到红方，也可能轮到黑方。程序不能从不存在的信息中可靠推断，因此恢复未知局面时采用最小且真实的交互：自动识别棋盘，用户选择当前行棋方。

## UI 变更

- “搜索秒”默认值由 5 改为 1，保留 1～60 秒可调范围。
- “同步 FEN”改为“同步当前棋盘”。
- 点击“同步当前棋盘”不再弹出文本输入框。
- 如果程序已经在失步恢复中识别出一个未知棋盘，直接复用该识别结果；否则立即截屏并执行现有全盘识别。
- 使用“当前行棋”下拉框的红方或黑方作为该局面的行棋方。
- 同步成功后显示“当前棋盘已同步，请开始辅助”。
- 无法识别时显示“无法识别当前棋盘，请重新校准”，不要求用户输入 FEN。

## 状态与数据流

### 正常落子

```text
每 0.2 秒截图
  -> 连续两帧确认变化
  -> MotionTracker 还原合法走法
  -> GameState 记录走法与局面版本
  -> 默认搜索 1 秒
  -> 显示推荐
```

完整走法历史、局面版本、悔棋和重复局面逻辑保持不变。

### 未知局面恢复

```text
MotionTracker 连续无法解释变化
  -> Calibration 全盘识别
  -> 若匹配历史快照：自动恢复
  -> 若为未知棋盘：缓存识别结果并停止辅助
  -> 提示选择当前行棋方并点击“同步当前棋盘”
  -> GameState 以该棋盘建立新基点，旧 moves 清空
```

同步按钮优先消费缓存棋盘，避免重复识别和额外等待。没有缓存时才重新截图识别。

## 代码边界

### `app.py`

- 增加模块常量表示默认搜索秒数和采样周期，避免两处等待值漂移。
- 删除普通 UI 的 FEN 弹窗入口。
- 用 `sync_current_board()` 替代 `sync_fen()`。
- `needs_sync` 事件继续携带已经识别的棋盘，但提示语改为普通用户可理解的操作说明。
- 同步成功后继续复用现有 `synced_position` 启动路径和 `GameState.start()`，不新增状态管理层。

### 其他模块

`game_state.py`、`board_recognition.py` 和 `pikafish_engine.py` 不需要新增架构。已有 `board_to_fen()` 仍作为内部引擎协议使用，但不出现在普通 UI 中。已有 `fen_to_board()` 可保留为内部兼容能力，本次不为删除内部代码扩大改动范围。

## 错误处理

- 辅助运行中点击同步：提示先停止辅助，避免并发改写状态。
- 有缓存恢复棋盘：不再次截图，直接按用户选择的行棋方同步。
- 无缓存且全盘识别成功：同步识别结果。
- 无缓存且识别失败：保持原状态，提示重新校准。
- 当前行棋方未选择到合法值：拒绝同步并提示选择红方或黑方。
- 引擎 1 秒内未完成：沿用现有超时和进程恢复机制。

## 测试与验收

自动测试至少覆盖：

1. 默认搜索预算为 1 秒。
2. 采样周期为 0.2 秒，循环内所有等待统一使用该值。
3. `AssistantApp` 不再提供 `sync_fen()` 普通操作入口。
4. 有缓存棋盘时，“同步当前棋盘”不调用截图或全盘识别。
5. 同步使用下拉框选择的当前行棋方，并生成正确的内部基点。
6. 无缓存时可通过现有全盘识别同步。
7. 识别失败不覆盖已有状态。
8. 现有完整历史、悔棋、重复局面、失步恢复和引擎测试继续通过。

Windows 人工验收：

1. 标准局面落子后，普通环境下约 2 秒内出现推荐。
2. 制造未知中盘后，界面不出现 FEN 或技术协议输入框。
3. 选择当前行棋方并点击“同步当前棋盘”，可继续辅助。
4. 红方、黑方各验证一次同步后的推荐时机。

## 明确不做

- 不识别 JJ 象棋界面上的“轮到谁”特效；该方案依赖皮肤和界面位置，升级后容易失效。
- 不承诺 1 秒搜索达到数学意义上的绝对最优；用户可把搜索秒数调高来换取更深搜索。
- 不删除内部 FEN 表示；Pikafish 仍需要标准局面协议。
- 不用单帧判断替代两帧稳定确认；约 0.2 秒收益不足以抵消动画中误判风险。
